# ADR-0004 — CI, security and release

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decisions covered:** DEC-11, DEC-25, DEC-32, DEC-33, DEC-34, DEC-35, DEC-37, DEC-38, DEC-41

## Context
At baseline there was no CI, no security tooling and no release process. Two other decisions shape this area:
there are no git hooks (DEC-28) and no update bot (DEC-29), so **CI is the only automated safety net**. The owner
asked for tool options per security category (SAST, DAST, SCA, secret scanning) rather than a single bundle.

## DEC-11 — PyPI with trusted publishing, plus GitHub Releases
- **Decision:** Publish to PyPI through trusted publishing (OIDC, no stored tokens), and create a GitHub Release
  for each version.
- **Alternatives considered:** *GitHub Releases only* (install from the git URL or a wheel; no PyPI account):
  not chosen.
- **Consequences:** Users can run `pipx install beck-bios`. Stage 10 handles the human-only setup (pending
  publishers, protected environments).

## DEC-25 — GitHub, with thin CI YAML
- **Decision:** Use GitHub features, but make every check a local `uv run …` command that CI only calls. Moving to
  another CI host means rewriting only the YAML.
- **Alternatives considered:**
  - *Strictly portable*: avoid GitHub-only services where an alternative exists (e.g. Renovate instead of
    Dependabot, no CodeQL); more setup. Not chosen.
  - *Full GitHub*: use GitHub-native features without portability constraints. Not chosen.
- **Consequences:** CI `run:` lines must match the commands in AGENTS.md. GitHub-only features (rulesets,
  environments, issue forms) are accepted where they're settings or thin wrappers.

## DEC-32 — SAST: ruff's `S` rules
- **Decision:** Static security analysis comes from ruff's `S` rule set (flake8-bandit), in the normal lint step.
- **Alternatives considered:** *Bandit* (the original, mostly redundant with ruff `S`), *Semgrep CE* (deeper
  pattern matching, more noise) and *CodeQL* (dataflow analysis; GitHub-only): not chosen.
- **Consequences:** No extra tool. MD5 is flagged by `S324`; the fix is `usedforsecurity=False` (step 03.6), not an ignore.

## DEC-33 — Runtime testing: a Samba container
- **Decision:** The runtime ("DAST"-equivalent) testing is a set of integration tests against a real Samba server
  in a container.
- **Alternatives considered:** Classic DAST tools (OWASP ZAP, Nuclei) attack web endpoints; BECK has none, so they
  would scan nothing. Also offered: *hypothesis* fuzzing of the parser (recommended during planning), *Atheris*
  coverage-guided fuzzing, and *skipping runtime testing*. Not chosen.
- **Consequences:** Stage 05 adds the container (DEC-40) and a Linux-only CI job, since GitHub's macOS and Windows
  runners can't run Linux containers.

## DEC-34 — SCA: Trivy
- **Decision:** Trivy scans dependencies for vulnerabilities and licenses on every PR and weekly. It's pinned by
  version with a verified checksum.
- **Alternatives considered:** *pip-audit* (PyPA, lightweight; recommended during planning), *OSV-Scanner* and
  *GitHub dependency-review* (GitHub-only, diff only): not chosen.
- **Consequences:** Step 02.13 must confirm that Trivy reads `uv.lock`, falling back to the generated
  `requirements.txt`. License findings are reported but don't fail the build until the owner records a policy.
  Trivy also produces the release SBOM (DEC-37).

## DEC-35 — Secret scanning: gitleaks
- **Decision:** gitleaks scans the PR's commit range on each PR, and the full history weekly. It's pinned with a
  verified checksum, and findings are redacted in logs.
- **Alternatives considered:** *TruffleHog* (can verify live keys), *detect-secrets* (baseline-file workflow) and
  *GitHub push protection* (a setting; GitHub-only): not chosen.
- **Consequences:** Fake test credentials must be clearly fake and allow-listed (`beck-test-password`).

## DEC-37 — Release supply chain: attestations and an SBOM
- **Decision:** PyPI attestations (produced automatically by trusted publishing) and a CycloneDX SBOM generated by
  Trivy, attached to each GitHub Release.
- **Alternatives considered:** *GitHub artifact attestations* (`actions/attest-build-provenance`; GitHub-only) and
  *none*: not chosen.
- **Consequences:** No extra tool beyond Trivy. Steps 10.5 and 10.6 implement it.

## DEC-38 — Conventional Commits checked by commitizen
- **Decision:** CI runs `uvx --from commitizen cz check` over the PR's commits.
- **Alternatives considered:** *a PR-title check action* (title only; GitHub-only) and *no enforcement*: not chosen.
- **Consequences:** CI checks out the PR head SHA, because GitHub's synthetic merge commit wouldn't pass. Commits
  from before the roadmap are never checked. git-cliff (DEC-20) relies on this format.

## DEC-41 — Release pre-flight: twine check and TestPyPI
- **Decision:** `uvx twine check --strict` on every build. Release-candidate tags publish to TestPyPI first.
- **Alternatives considered:** *twine check only* and *neither* (rely on PyPI rejecting uploads, though a
  published version can't be overwritten): not chosen.
- **Consequences:** The first public version goes through an rc rehearsal (step 10.9).

## Shared practice: pinning
All third-party GitHub Actions are pinned to full commit SHAs, and downloaded tools (gitleaks, Trivy) to
versions with verified checksums. Floating tags have been hijacked before (for example `tj-actions/changed-files`
in March 2025). The monthly routine (`docs/maintenance.md`) refreshes the pins.

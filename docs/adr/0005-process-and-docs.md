# ADR-0005 — Process and documentation

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decisions covered:** DEC-14, DEC-16, DEC-20, DEC-30, DEC-31, DEC-39, DEC-51, DEC-52, DEC-71, DEC-72

## Context
The roadmap is executed one step at a time, often by AI agents. The process has to keep each change small and
reviewable, keep the history useful for generating a changelog, and keep humans in control of everything that
leaves the machine (see DEC-43 in [ADR-0002](0002-ai-agent-support.md)).

## DEC-14 — One branch and PR per stage, one commit per step
- **Decision:** Each stage gets a branch `stage/NN-slug` and one pull request. Each step is one commit with a
  Conventional Commits message, and CI must be green before merging.
- **Alternatives considered:** *a PR per step* (finest granularity, most review overhead) and *commit straight to
  main* (fastest, no review gate): not chosen.
- **Consequences:** Step commit messages are pre-written in the stage files. Stage 11 uses one branch per feature
  instead.

## DEC-16 — Progress tracked in Markdown only
- **Decision:** The checkboxes in `roadmap/*.md` are the only progress tracker.
- **Alternatives considered:** *Also mirror stages as GitHub milestones and issues*: not chosen.
- **Consequences:** Works offline and with any agent. GitHub issues are for bugs and requests, not for roadmap steps.

## DEC-20 — Changelog generated by git-cliff
- **Decision:** `CHANGELOG.md` is generated from Conventional Commits by git-cliff, in Keep a Changelog layout.
- **Alternatives considered:** *a hand-written Keep a Changelog* (best prose, easy to forget), *release-please*
  (bot-driven release PRs; GitHub Actions only) and *towncrier* (news fragments; more ceremony): not chosen.
- **Consequences:** Never edit `CHANGELOG.md` by hand. Commits from before the roadmap go under an "Earlier
  history" entry (step 08.6).

## DEC-30 — Documentation as Markdown in the repository
- **Decision:** No docs website. Everything is Markdown that GitHub renders and agents read directly.
- **Alternatives considered:** *an MkDocs site on GitHub Pages* and *Sphinx with Read the Docs*: not chosen.
- **Consequences:** The link test (DEC-42) is the only docs tooling. The CLI reference is generated into Markdown
  (step 08.4).

## DEC-31 — Short custom code of conduct
- **Decision:** A short "Code of conduct" section inside `CONTRIBUTING.md`; no separate file.
- **Alternatives considered:** *Contributor Covenant* (the most widely used; recognized by GitHub's community
  profile; recommended during planning) and *none*: not chosen.
- **Consequences:** The owner provides the contact channel for conduct reports (step 12.2).

## DEC-39 — Merge commits
- **Decision:** Stage PRs are merged with a merge commit, so the step commits stay on `main`.
- **Alternatives considered:** *rebase-merge* (linear history; recommended during planning) and *squash with a
  Conventional title* (one changelog line per stage, contradicting one commit per step): not chosen.
- **Consequences:** `main` has one merge commit per stage marking where it landed. git-cliff reads the step commits.
  Squash and rebase merging are disabled in repository settings (step 02.16).

## DEC-51 — Stage 03 signed off on a VM
- **Date:** 2026-11-04 (step 03.13).
- **Context:** Step 03.13 and stage 03's acceptance criteria asked for an end-to-end check on a real Recalbox. The
  owner ran Recalbox 10.1.1 x86_64 in a QEMU VM instead, and BECK ran against it with the owner's own files and the
  VM's real report and Samba server.
- **Decision:** Accept the VM run as the sign-off for step 03.13 and stage 03.
- **Alternatives considered:**
  - *Run the checks on a real Recalbox* (recommended by the agent): the only way to test real hardware. Not chosen.
    The owner gave no further reason.
- **Consequences:**
  - Not verified: real hardware, and BECK choosing direct TCP by itself on port 445. The VM's SMB port was forwarded
    from host port 4445, so BECK used NetBIOS mode there. Direct TCP worked against the VM only when forced by a
    throwaway test script, and BECK's own choice is covered by a test with the fake server.
  - This decision covers stage 03 only. Step 04.1 and the stage 10 release check still ask for a real device.

## DEC-52 — Step 04.1 runs on a VM
- **Date:** 2026-11-04 (step 04.1).
- **Context:** Step 04.1 and DEC-26 asked for a real Recalbox, and DEC-51 covered stage 03 only.
- **Decision:** Run step 04.1 on the Recalbox 10.1.1 VM. The real-device run moves to the release check in step 10.11.
- **Alternatives considered:**
  - *Run it on a real Recalbox* (recommended by the agent if a device was available): covers real hardware and port 445.
    Not chosen. The owner gave no further reason.
  - *Wait until a device is available*: keeps stage 04 blocked. Not chosen.
- **Consequences:** The transport's first real-hardware run is late, so a problem found in step 10.11 means reworking
  it close to release. The VM runs the same Recalbox software, so the main gap is real network conditions.

## DEC-71 — Step 10.11 is three commits
- **Date:** 2026-11-11 (step 10.11).
- **Context:** Step 10.11 lists one commit, `chore(release)!: 1.0.0`. A final release needs a release candidate first, which needs its own release
  commit, and the changelog would show the removals only as "Breaking: release: 1.0.0", because it's made from commit messages (DEC-20).
- **Decision:** An exception to DEC-14's one commit per step, for this step only: `feat!: remove check_bios.py, requirements.txt and the bare beck
  alias`, with the 1.0 criteria; then `chore(release): 1.0.0rc1`; then `chore(release): 1.0.0`, after the owner's run of the release candidate
  on a real device.
- **Alternatives considered:** *One commit, as the step says, with the release candidate done separately anyway:* the release notes would have to
  explain the removals. Not chosen. The agent recommended three commits, and the owner gave no further reason.
- **Consequences:** The step's box is ticked in the last of them, once `1.0.0` is on PyPI.

## DEC-72 — 1.0's end-to-end run is on the VM
- **Date:** 2026-11-11 (step 10.11).
- **Context:** DEC-51 and DEC-52 signed stages 03 and 04 off on the Recalbox 10.1.1 VM, and moved the run on real hardware to step 10.11, as a
  1.0 criterion. At 10.11, the owner asked the agent to do the run. `recalbox.local`, which the owner's settings name, didn't resolve, and the only
  Recalbox reachable was the VM.
- **Decision:** Supersedes DEC-52's move of the real-device run to 10.11. The 1.0 end-to-end run is on the VM: the installed `1.0.0rc1`, the owner's
  own BIOS files, a dry run, a real run with `--verify`, and a second dry run.
- **Alternatives considered:** *Turn a real Recalbox on, so that `recalbox.local` resolves,* or *give its address:* both keep the criterion as it was.
  Not chosen. The owner gave no further reason.
- **Consequences:** BECK 1.0 has never run on real hardware, and the README says so. What a real device can differ in, such as its network, its
  Samba settings and its speed, is untested, so the first reports from real devices matter.
